# PRD: Ore — кроссплатформенный редактор SQLite

Status: Ready for build · Date: 2026-10-04

> Название: **Ore** (утверждено 2026-10-04). Дизайн-система — Caliper. Легенда имени: руда — ценное внутри сырых данных; короткое, свободное в dev-нише (проверено поиском: Caliper занят 4+ проектами, Quarry — Wikimedia SQL-тул, Ori — марка Moon Studios + ori.co).

## 0. Допущения (явно, вместо вопросов)

- «Импортировать для macos/windows/linux» трактуется как **собирать и распространять** готовые дистрибутивы (установщики/бинарники) под все три ОС, а не импорт данных.
- Целевой пользователь — вы сами и разработчики/аналитики, работающие с локальными SQLite-файлами; GUI-инструмент, а не библиотека.
- Одиночный разработчик; бюджет на инфраструктуру минимальный (CI бесплатный, подпись macOS — по возможности).
- Редактирование локальных файлов `.db` / `.sqlite` / `.sqlite3`, включая WAL. Сетевые СУБД — вне скоупа.

## 1. Framing

**User:** разработчик или аналитик, у которого на диске лежат SQLite-файлы (бэкенды, мобильные приложения, прототипы) и который сейчас копается в них через CLI `sqlite3`.

**Problem:** CLI неудобен для просмотра и правки данных; DB Browser for SQLite выглядит устаревше и тормозит на больших таблицах; нормального импорта/экспорта и SQL-консоли в одном лёгком инструменте нет.

**Value:** открыть файл за 2 секунды, увидеть схему, отредактировать данные как в таблице, выполнить SQL, выгрузить результат в CSV/JSON — в одном нативном приложении весом ~10 МБ.

**Primary job:** безопасно посмотреть и отредактировать данные в SQLite-файле и выполнить SQL за минимальное число шагов.

## 2. User stories

- **US-1 (открытие):** Как разработчик, я хочу открыть БД через диалог или drag&drop, чтобы начать работу без терминала.
  - AC: [ ] открытие `.db/.sqlite/.sqlite3` любой валидной БД; [ ] понятная ошибка, если файл не SQLite; [ ] список недавних файлов; [ ] read-only открытие при блокировке другим процессом.
- **US-2 (схема):** Как разработчик, я хочу видеть дерево схемы (таблицы, view, индексы, триггеры, колонки с типами), чтобы понимать структуру.
  - AC: [ ] дерево обновляется после DDL; [ ] DDL таблицы показывается целиком (CREATE statement).
- **US-3 (данные):** Как аналитик, я хочу просматривать и править данные в гриде с пагинацией и сортировкой, чтобы работать с таблицами в тысячи строк.
  - AC: [ ] пагинация/virtual scroll — не грузит всю таблицу; [ ] редактирование ячейки с подтверждением; [ ] NULL и BLOB различимы; [ ] добавление/удаление строк; [ ] фильтр по колонке.
- **US-4 (SQL):** Как разработчик, я хочу писать и запускать SQL с подсветкой и историей, чтобы делать выборки и изменения.
  - AC: [ ] подсветка синтаксиса; [ ] запуск по Ctrl/Cmd+Enter; [ ] результат в гриде; [ ] история запросов между сессиями; [ ] предупреждение на потенциально разрушительные стейтменты (DELETE/DROP без WHERE).
- **US-5 (импорт/экспорт):** Как аналитик, я хочу импортировать CSV/JSON в таблицу и экспортировать таблицу или результат запроса в CSV/JSON/SQL, чтобы гонять данные между системами.
  - AC: [ ] импорт CSV с выбором разделителя и кодировки; [ ] прогресс и количество импортированных строк; [ ] экспорт текущего результата запроса одной кнопкой.
- **US-6 (упаковка):** Как мейнтейнер, я хочу собирать дистрибутивы для трёх ОС одной командой/пушем, чтобы распространять приложение.
  - AC: [ ] `.dmg` (macOS), `.msi`/`.exe` (Windows), `.AppImage`/`.deb` (Linux); [ ] сборка в GitHub Actions по тегу; [ ] артефакты прикладываются к release.

## 3. User flows

**Flow: Открыть и отредактировать**
1. Запуск приложения → 2. drag&drop файла (или Recent) → 3. дерево схемы слева → 4. клик по таблице → грид с данными → 5. двойной клик по ячейке → правка → Enter → UPDATE подтверждается и выполняется.
*Ошибки/края:* файл не SQLite → человекочитаемая ошибка; файл заблокирован → read-only режим с баннером; пустая БД → empty state с кнопкой «Создать таблицу (SQL)».

**Flow: SQL-запрос**
1. Вкладка SQL → 2. ввод запроса → 3. Ctrl/Cmd+Enter → 4. грид результата + время выполнения + число строк.
*Ошибки:* синтаксическая ошибка → сообщение с номером строки; долгий запрос → возможность прервать (interrupt); `SELECT` без `LIMIT` → авто-лимит + кнопка «догрузить».

**Flow: Импорт CSV**
1. Импорт → выбор файла → 2. превью первых строк, выбор разделителя/кодировки/целевой таблицы (создать новую или в существующую) → 3. импорт транзакцией → итог: сколько строк добавлено.
*Ошибки:* несовпадение колонок; некорректные типы; пустой файл.

## 4. Scope

- **MVP:** US-1…US-6 в объёме acceptance criteria (открытие, схема, грид с редактированием, SQL-консоль, CSV/JSON импорт-экспорт, сборка под 3 ОС). Больше ничего — это уже сквозной продукт.
- **Next:** read-only режим для всего приложения; attach нескольких БД; панель PRAGMA / integrity check; сохранённые запросы; автопроверка «WHERE отсутствует» настраиваемым уровнем строгости.
- **Later:** EXPLAIN QUERY PLAN визуализация, ER-диаграмма схемы, автосообщение обновлений (updater), плагины/темы.
- **Out of scope:** MySQL/Postgres и любые сетевые СУБД; совместное редактирование; мобильные платформы; шифрование (SQLCipher) — до явного спроса.
- Приоритизация — MoSCoW по принципу «выкини и проверь, выполняется ли primary job»: без US-1…US-3 продукт мёртв (Must), US-4…US-6 делают его полноценным (Must для релиза), Next — Should, Later — Could.

## 5. Технический стек и упаковка (рекомендация)

- **Рекомендуемый стек: Tauri 2 + Rust (rusqlite, bundled SQLite) + TypeScript + Svelte или React.**
  - Плюсы: бинарь 5–15 МБ против ~100+ МБ у Electron; нативный rusqlite без возни с пересборкой нативных модулей Node; встроенный bundler даёт все целевые форматы; GitHub Actions matrix из коробки.
  - Альтернатива: Electron + better-sqlite3 — если хотите остаться полностью в JS; проще в разработке, но тяжеловесно и требует rebuild нативного модуля под каждую платформу.
- **Архитектура:** фронт не общается с SQLite напрямую — только через Tauri-команды (`open_db`, `list_tables`, `query`, `exec`, `import_csv`…), каждая возвращает строго типизированный JSON. SQL из UI передаётся как параметр, но построение UPDATE/INSERT при редактировании грида — на стороне Rust (параметризованные запросы). Чтение данных — чанками `LIMIT/OFFSET` или по rowid-курсору.
- **Ключевые библиотеки:** Monaco (SQL-редактор), TanStack Table + виртуализация (грид), `rusqlite` + `csv` + `serde_json` (бэкенд).
- **Сборка:** `tauri build` → dmg (macOS), NSIS/msi (Windows), AppImage/deb/rpm (Linux); GitHub Actions с matrix `macos-latest / windows-latest / ubuntu-latest`, релиз по git-тегу. Подпись и нотаризация macOS — опционально (нужен Apple Developer ID, $99/год); без них Gatekeeper покажет предупреждение.

## 6. UX & visual brief

> Реализация: папка `design/` — направление «**Caliper**» (flat, волосяные линии 1px, три уровня поверхности, петрольный акцент). Обзор — `design/index.html`, токены обеих тем — `design/tokens.css`, пояснения — `design/design-brief.md`. Макеты проверены визуально в тёмной и светлой темах.

- **Screens:** главное окно (сайдбар схемы + грид данных, вкладки таблиц), вкладка SQL (редактор + панель результата), диалог импорта/экспорта, настройки, empty state.
- **Interactions:** двойной клик — правка ячейки; Ctrl/Cmd+Enter — выполнить; drag&drop файла на окно; контекстное меню грида (copy as JSON/CSV, set NULL); тосты для подтверждений записи.
- **Design direction:** плотный, «инструментальный» интерфейс в духе TablePlus/DataGrip — компактные шрифты, минимальная хромированность, тёмная и светлая темы, нативные меню и хоткеи каждой ОС. Чего избегать: перегруженные диалоги и вкладки-леса в стиле DB Browser. Платформенные конвенции (Cmd на macOS, Ctrl на Win/Linux) — обязательны.

## 7. Metrics

- **Success:** время «скачал → открыл свою БД → изменил значение» меньше 5 минут на чистой машине; собстренное dogfooding как основной инструмент (цель — переключиться с текущего способа работы полностью).
- **Counter-metric:** ноль случаев порчи данных (незапланированные изменения/потеря) — редактор БД не имеет права молча терять данные.
- **Validation (дёшево):** dogfooding 2 недели + дать 3–5 знакомым разработчикам сборку под их ОС; гипотеза подтверждена, если ≥3 из 5 используют его повторно без напоминания. Провал, если всем нужен был только просмотр без редактирования (тогда резать US-3/US-5 и делать лёгкий вьюер).

## 8. Risks & open questions

- **R1. Большие БД** (миллионы строк): фризы UI → пагинация на SQL-уровне + виртуализация грида; никогда не `SELECT *` целиком. → Mitigation: лимит строк в MVP, курсорное чтение.
- **R2. Кросс-компиляция и CI:** сборка под 3 ОС локально мучительна → GitHub Actions matrix с первого дня, а не в конце.
- **R3. Подпись macOS:** неподписанный dmg пугает пользователей Gatekeeper'ом → в MVP ок с инструкцией «ПКМ → Открыть»; подпись/нотаризация — в Next при появлении реальных пользователей.
- **R4. Порча данных при редактировании:** опечатка в UPDATE без WHERE → подтверждение destructive-стейтментов + явная транзакция на каждую правку + подсчёт затронутых строк.
- **R5. Выбор стека (Q1):** Tauri против Electron — рекомендация Tauri; решение блокирует старт каркаса, но не дизайн. **Q2:** нужна ли автопроверка обновлений в MVP — по умолчанию нет.
